# DEV-8 handoff: Mohar Console

**Status (Fri ~17:00): MVP, Strong and most of Polish built. 20 of 20 replay/local checks and 14 of 14 REAL-data checks pass (real `meter-001.mohar.eth` on Sepolia -> public Mohar devnet, while the board was running its soak). Not yet tested with real Web Serial (a person must do that: dashboard/README.md).**

## What exists
`dashboard/`: Vite + React + TypeScript + Tailwind static site. `npm run build` → `dashboard/dist`; `npm run dev` → http://127.0.0.1:8088.
No backend, no analytics, no secrets in the code. Pinned: react 18.3.1, vite 5.4.21, viem 2.57.16, recharts 2.15.0, tailwind 3.4.17, lucide-react 0.468.0.
The earlier vanilla-JS build is in `dashboard/old/` (kept for reference; its ENS reader was ported to `src/lib/ens.ts`).

| Page | What it does |
|---|---|
| Demo Console | 7 scenario buttons + **Apply meter scenario** (writes one character to the Pico over Web Serial), connect Pico / ESP8266, REPLAY picker, the live **8-stage pipeline** (rail + cards, each opens a detail panel), device event log |
| Overview | Identity, SEPOLIA / MOHAR DEVNET / REPLAY badges, power, device-counted vs on-chain-confirmed energy side by side, mode, credit, arrears, signal health, latest AI decision, chart, last confirmed report |
| Meter | Pulses, window, power (labelled ESTIMATED), signal integrity (valid / glitch / stuck), sensor explorer with "Not installed" entries (no invented charts) |
| Verified report | One report from pulse to ledger: status (preparing / submitted / mined / confirmed), AI request ID, key used, frame results |
| AI insights | Latest assessment, "AI side / fixed check / ledger hold / final" explanation, decision timeline from real events, history from the ledger |
| Credit & ledger | Credit, arrears, tariff, quota, holds, top-ups, CREDIT_STOP explained as arrears (never disconnection); wallet buttons for top-up and clear-hold |
| Usage | Ranges (all / today / 7 / 30 days) over on-chain reports; explicit "not enough data" state; no cost or forecast (credit is devnet ETH) |
| Identity & access | ENS records, root consistency (ENS vs account `root()` vs device), per-record permissions, **live dry-run of "may this address edit this record?"** via ENS `eth_call` with no key |
| Activity & audit | Searchable list of on-chain reports; each expands to fields, the sensors word, transaction and the four frame results |
| Settings | ENS name, devnet RPC (local / EF devnet), testing-only manual addresses, theme |

Data: ENS on Sepolia through the Universal Resolver (with fallback RPCs, because a single public endpoint dropped calls in testing); the devnet RPC for ledger `status()`, `Report` events, receipts, paymaster quota; Web Serial for `METER` / `EV` lines (`docs/event-protocol.md`). **Pipeline stages are derived only from received events** (`src/lib/events.ts`); nothing advances on a timer.

REPLAY: `dashboard/replay/*.log` generated by `replay/make-replays.mjs` (copied to `public/replay/`). **These are synthesised to follow the protocol, not recorded from a run**, and the UI badges them REPLAY. Auto-start: `?replay=surge-inspect.log&speed=20`. Settings can also be set by URL (`?chainRpc=…&manualLedger=…&ensName=…`).

## ENS-3 (Fri ~16:55): discovery and permission demo

**Built:** `src/pages/Permissions.tsx` (used by the Identity & Access page; replaces the earlier small card), `public/demo-roles.json`
(the public addresses of the demo personas), `test/ens3.py`. Rebuild with `npm run build`; run the test with
`uv run --no-project --with selenium python dashboard/test/ens3.py`. It reads Sepolia only and sends nothing.

**What the panel does:** a table of records vs roles (owner, maintenance, uploader, stranger), labelled as **Sepolia identity records**
that do not control the meter's devnet contracts; five one-click cases plus free choice of account, record and value; **Try this edit**
dry-runs `setText` with `eth_call` from the chosen account against the live resolver of the name (found through ENS) and shows the
contract's real answer, labelled "Simulated against the live contract (eth_call on Sepolia at <time>). Nothing is sent." The previous
answer is cleared the moment a new check starts (found in testing: it was briefly possible to read the old answer as the new one).
If `window.ethereum` exists, a wallet can connect and send the real edit; the page first checks the wallet's account against the
resolver and only then asks it to sign, and it never handles a key. **The wallet path was not run** (no browser wallet here).
